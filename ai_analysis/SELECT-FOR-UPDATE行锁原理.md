# `SELECT ... FOR UPDATE` 行锁原理与本项目用法

整理日期：2026-09-24。

本文解释下面这条 SQL 是怎样工作的，以及它在本项目中怎样协调下单和购物车写入：

```sql
SELECT id FROM user WHERE id = #{id} FOR UPDATE;
```

先说结论：在 MySQL InnoDB 中，这是一条**当前读（locking read）**。它查找匹配的 `user` 记录，并为事务取得该记录上的排他锁。另一个事务若也想对同一记录取得冲突锁，通常要等前一个事务提交或回滚。但这条 SQL **不会禁止所有人读取这个用户，更不会自动锁住购物车表**。本项目把用户行当作同用户写操作的“互斥闸门”：每条相关写流程都先取得同一把用户行锁，然后在同一事务中继续操作购物车或订单。

## 1. 这条 SQL 每一段是什么意思

```sql
SELECT id               -- 只取 user 记录的 id
FROM user               -- 查询 user 表
WHERE id = #{id}        -- 用当前登录用户的 id 定位一条记录
FOR UPDATE;             -- 当前读，并请求该记录的排他锁
```

`#{id}` 是 MyBatis 参数占位符，执行时会安全地绑定用户 ID。它不是字符串拼接。若 `id` 是 `user` 表的主键（本项目按用户 ID 定位），数据库通常可以通过唯一索引直接定位到该用户记录。

普通 `SELECT` 只需要读数据；`SELECT ... FOR UPDATE` 除了读，还表示：“我准备在这个事务里依据这条记录继续做事，请给我一个冲突写操作不能同时持有的锁。”这类查询也叫锁定读。

## 2. 数据库具体锁住什么

本项目 SQL 锁住的是 `user` 表中 `id = 当前用户ID` 对应的那条记录（InnoDB 索引记录），不是：

- 整张 `user` 表；
- 这个用户在其他表中的所有记录；
- 这个用户的所有 HTTP 请求；
- 所有对该用户数据的普通读取。

若另一事务要更新同一条 `user` 记录，或者用 `FOR UPDATE` / `FOR SHARE` 等需要冲突锁的方式锁同一记录，就会受锁约束，等待、超时或遇到死锁处理。不同用户对应不同记录，通常不因这把记录锁互相等待。

在 InnoDB 中，行锁依附于索引记录。对已存在的唯一主键值做等值查找，通常锁定命中的记录本身；若查询条件、索引或事务隔离级别不同，范围扫描还可能涉及间隙锁或 next-key 锁。这里的关键设计是用单个用户主键等值查找，作为稳定的每用户协调点。

## 3. 为什么必须放在事务中

行锁不是执行完 SQL 就立刻释放。通常，InnoDB 会在当前事务 `COMMIT` 或 `ROLLBACK` 时释放它。因此，执行顺序应是：

```text
开启事务
  → SELECT ... FOR UPDATE（取得 user 行锁）
  → 查询/修改购物车
  → 创建订单与订单明细
  → 清空购物车
提交事务（释放锁）
```

在项目里，`UserOrderService.submit` 和购物车写方法标了 `@Transactional`，之后调用 `userWriteLock.lock()`。Spring 事务使这些 mapper 操作在同一事务/数据库连接中执行；数据库才会把 `FOR UPDATE` 取得的锁一直保留到整个业务事务结束。

如果锁定查询在事务外单独执行，自动提交模式可能会在这条语句结束时就提交并释放锁。这样后续“读购物车、下单、清空购物车”并没有被这把锁保护，达不到目的。

## 4. 第二个请求究竟会不会被挡住

要区分第二个请求正在做什么：

| 第二个请求的操作 | 是否通常会等这把锁 | 原因 |
| --- | --- | --- |
| 对同一用户行再次执行 `SELECT ... FOR UPDATE` | 会等待前一个事务释放锁 | 两边都要取得冲突的排他锁 |
| 更新同一条 `user` 记录 | 会等待或发生锁冲突 | 更新需要修改被锁住的索引记录 |
| 对 `user` 行做普通 `SELECT` | 通常不会等待 | InnoDB 普通一致性读通常读取 MVCC 版本，不需要这把排他记录锁 |
| 直接更新 `shopping_cart` 行，但没有先锁 `user` 行 | 不会仅因为 `user` 行锁就自动等待 | `user` 与 `shopping_cart` 是不同记录；数据库不知道业务上要把它们作为同一个互斥区 |
| 先按约定锁 `user` 行，再读写该用户购物车 | 会先在锁用户行这一步等待 | 应用主动让相关写路径争用共同的用户锁 |

所以，“锁用户行防止第二个请求读写”是一种简写，严格说应该是：**第二个遵守同一加锁协议的写请求，在自己的流程读写购物车之前，会先尝试锁同一用户行；若第一个事务还未结束，它就会在那里等待。**这不是 MySQL 自动把该用户的所有表都封住。

普通读接口仍可能读取到符合其隔离级别的已提交版本。此设计主要协调写流程，避免相关的写操作同时依据同一份购物车做决定。

## 5. 用两个同时下单请求看完整过程

假设用户 U 的购物车里有一份宫保鸡丁。两个下单请求几乎同时到达：

```text
事务 A                                      事务 B
──────────────────────────────────────      ──────────────────────────────────────
开启事务                                    开启事务
锁 user(U)，成功
                                            尝试锁 user(U)，等待
读取 U 的购物车：有宫保鸡丁
插入订单 A 和明细 A
删除 U 的购物车
提交，释放 user(U) 锁
                                            获得 user(U) 锁
                                            读取 U 的购物车：为空
                                            返回购物车为空，不创建订单 B
```

第二个请求不是被禁止“读数据库”，而是它在约定的锁点等第一个事务完成；随后才读取购物车。由于第一个事务已经提交清空购物车，第二个读到的是更新后的业务状态。

另一个顺序也合理：若“加购”请求先取得 U 的用户锁并提交，加购就先完成；下单随后取得锁，会把加购后的购物车读入订单。也就是说，锁不仅防止重复消费，还让竞争操作有一个明确的先后次序。

## 6. 为什么锁用户行，而不是先锁购物车行

购物车可能为空。若设计为先查购物车行再锁它，空购物车没有现成记录可供锁定；并且首次加购、清空、下单等路径要覆盖的情况较多。用户记录一般稳定存在，因此可用它作为“每用户互斥锁”的载体。

项目中的代码位置：

- [UserMapper.java](../sky-server/src/main/java/com/sky/mapper/UserMapper.java)：定义 `lockById`，SQL 为 `select id from user where id = #{id} for update`。
- [UserWriteLock.java](../sky-server/src/main/java/com/sky/service/support/UserWriteLock.java)：从当前登录上下文获取用户 ID，再执行 `lockById`。
- [UserOrderService.java](../sky-server/src/main/java/com/sky/service/UserOrderService.java)：下单流程先调用用户锁，再读取购物车并创建订单。
- [ShoppingCartServiceImpl.java](../sky-server/src/main/java/com/sky/service/impl/ShoppingCartServiceImpl.java)：加购、减购、清空等写操作也先拿同一用户锁。

锁住一个用户行是较粗的粒度：同一用户的加购和下单会排队，即使请求碰巧修改不同菜品；不同用户之间则可以并行。选择这种实现，是用一些同用户操作间的等待，换取简单而一致的互斥规则。

## 7. 这个方案成立需要哪些条件

1. **存储引擎支持行锁。**本项目目标数据库是 MySQL/InnoDB；其他不支持相同锁语义的引擎不能直接假设效果相同。
2. **必须在有效事务中持锁。**`FOR UPDATE` 拿到的锁要覆盖后面的业务步骤，并到提交/回滚才释放。
3. **所有相关写路径都要先锁同一行。**加购、减购、清空、下单等若有一条路径跳过锁，它仍可能与锁内流程并发修改购物车。
4. **锁定顺序要一致。**多个事务若先后以不同顺序锁多条记录，可能互相等待形成死锁。数据库会中止其中一个事务，应用通常要妥善处理。
5. **锁不是幂等键。**它可把并发操作排队，但如果业务允许每个请求都各自创建新对象，单靠锁不能保证所有重试都只执行一次。需要“同一业务命令只处理一次”时，应再设计幂等键或唯一约束。

用户行锁在同一数据库实例的多个应用进程之间也有效，因为协调由数据库完成，不依赖某台服务器里的 Java `synchronized`。若应用部署多实例，本地 JVM 锁只管单个进程，而数据库行锁可让这些实例共同争用同一用户记录。

## 8. 总结

`SELECT id FROM user WHERE id = ? FOR UPDATE` 通过索引找到指定用户行，并在当前事务中取得该行的排他锁。持锁期间，第二个事务若也要锁/更新这条用户行，就要等待。项目让下单和购物车相关写流程都先争这把锁，因此第二个下单请求不会在第一个事务消费购物车的同时也读取并消费同一购物车。

它不会自动锁购物车表，也不会禁止普通读取。真正的业务保护来自三件事同时成立：**数据库行锁已取得、事务覆盖完整业务流程、所有相关写入口都遵守先锁用户行的约定。**
