# 购物车 SKU 匹配实现：新旧逻辑与优缺点

整理日期：2026-10-05。

本文对照 Git HEAD 中的旧代码与当前工作区的实现，说明购物车怎样判断两行是不是同一个 SKU，以及这种改动带来的好处、成本和边界。

## 1. 本项目里的 SKU 是什么

SKU 是可以独立购买、独立计数的一种商品选择。当前购物车里用于区分 SKU 的核心字段是：

```text
菜品 ID + 套餐 ID + 口味字符串
```

实际规则要求菜品 ID 和套餐 ID **恰好一个有值**：

```text
dishId=7, setmealId=null, dishFlavor="大份,少辣"  → 菜品 7 的“大份、少辣” SKU
 dishId=7, setmealId=null, dishFlavor="小份,少辣" → 另一种 SKU
 dishId=null, setmealId=3, dishFlavor=""           → 套餐 3 SKU
```

数量、价格、名称、图片不是用来判断“是不是同一个 SKU”的字段。数量是该 SKU 的件数；价格、名称、图片是商品信息快照。比较身份时把价格放进去会导致改价后同一商品被识别成新 SKU；把数量放进去则永远无法合并不同数量的同一 SKU。

## 2. 当前实现在哪里

关键逻辑分布在：

- [CartRules.java](../sky-server/src/main/java/com/sky/service/support/CartRules.java)：`identity` 校验商品身份并规范化口味；`same` 比较两个购物车项是否同 SKU。
- [ShoppingCartServiceImpl.java](../sky-server/src/main/java/com/sky/service/impl/ShoppingCartServiceImpl.java)：加购的 `merge`、减购的精确匹配。
- [ShoppingCartMapper.xml](../sky-server/src/main/resources/mapper/ShoppingCartMapper.xml)：当前仍提供动态查询，但加购和减购主要按用户查出购物车，再在 Java 中用 `same` 过滤。

当前的比较规则可概括为：

```java
same(a, b) =
    a.dishId 与 b.dishId 相等
    且 a.setmealId 与 b.setmealId 相等
    且 normalize(a.dishFlavor) 与 normalize(b.dishFlavor) 相等

normalize(null) = ""
```

代码使用 `Objects.equals` 比较 ID 与口味，并将 `null`、空字符串统一按无口味处理。由于菜品/套餐身份经过 `identity` 验证，正常入口不会出现“菜品和套餐 ID 都为空”或“二者同时有值”的不明确身份。

## 3. 旧逻辑：把请求对象作为动态查询条件

Git HEAD 中旧的加购逻辑大致是：

```java
ShoppingCart row = new ShoppingCart();
BeanUtils.copyProperties(dto, row);
row.setUserId(BaseContext.getCurrentId());
List<ShoppingCart> list = shoppingCartMapper.list(row);

if (!list.isEmpty()) {
    ShoppingCart first = list.get(0);
    first.setNumber(first.getNumber() + 1);
    shoppingCartMapper.updateNumberById(first);
} else {
    // 查询菜品/套餐，填名称、图片、价格，再插入
}
```

旧 `ShoppingCartMapper.xml` 的 `list` 使用动态 `<if>`：只有查询对象某字段不为 `null` 时，才把该字段加进 `WHERE`。因此口味条件是：

```xml
<if test="dishFlavor != null">
    and dish_flavor = #{dishFlavor}
</if>
```

旧减购也用同样的“复制 DTO → 补 userId → 动态 list → 取第一条”模式。

### 旧逻辑一个具体风险：`null` 会变成“不筛口味”

用户购物车里有：

```text
菜品 7，dish_flavor="大份,少辣"，数量 2
菜品 7，dish_flavor=""，数量 1
```

如果请求表示无口味时传 `dishFlavor = null`，MyBatis 的 `<if>` 不成立，生成的 SQL 不含 `dish_flavor` 条件。查询可能变成：

```sql
SELECT * FROM shopping_cart
WHERE user_id = ? AND dish_id = ?
ORDER BY create_time DESC;
```

而不是要求 `dish_flavor = ''`。结果集包含不同口味的多个 SKU；旧代码只取第一行，于是可能把有口味商品加一，或减错一个 SKU。具体误匹配哪行受排序和数据状态影响。

如果无口味稳定传空字符串 `""`，SQL 会加上 `dish_flavor = ''`，则能精确匹配。因此旧代码的正确性依赖调用方始终把“无口味”编码成空字符串，不能依赖 `null` 表达同一语义。DTO 缺字段、序列化差异或其他调用者都可能打破这个约定。

旧逻辑还有几个相关问题：

- 没有统一拒绝“菜品和套餐 ID 都没传”或“两个都传了”；动态 SQL 可能查不到，也可能变成过宽查询，后续只取结果第一条。
- `list` 返回多个结果时只更新/删除其中第一行，不会清理已有重复 SKU。
- 旧加购只有插入新购物车行时才查询商品来填价格、名称、图片；若匹配到旧行，只加数量，不刷新可能过期的商品快照。
- 加购/减购没有共同的用户行锁，两个并发请求可能同时读到旧数量，再都写同一个“旧数量 + 1”，从而丢失一次增加；并发首次插入也可能出现重复行。

## 4. 当前逻辑：先限制用户范围，再使用统一比较函数

### 第一步：验证身份与规范口味

`CartRules.identity(row)` 要求：

- 菜品 ID 与套餐 ID 恰好一个有值；
- 提供的商品 ID 必须大于 0；
- `dishFlavor == null` 时转换为 `""`。

加购会经 `hydrate` 调用 `identity`；减购会直接对 key 调用 `identity`。因此两条路径都按明确的商品类型和口味语义继续执行。

### 第二步：把查询范围固定为当前用户

加购 `merge` 查询：

```java
shoppingCartMapper.list(ShoppingCart.builder()
    .userId(row.getUserId())
    .build())
```

减购也是只按当前用户 ID 查列表。这个范围来自 `BaseContext`/`UserWriteLock` 得到的登录用户 ID，而不是从请求 DTO 采用一个任意 userId。

### 第三步：按三个身份字段逐行比较

加购通过：

```java
.filter(x -> rules.same(x, row))
```

减购逐行执行 `rules.same(row, key)`，找到精确匹配项后才减数量或删除。

这样即使查询结果里有同一道菜的多种口味，也不会因为请求没有口味条件就把它们一起当成候选 SKU。`null` 与 `""` 先规范化，避免同一个无口味 SKU 在不同调用方表示下被拆成两种。

### 第四步：加购归并所有精确匹配行

`merge` 对匹配行的数量求和，再加本次要加入的数量。确认每一行和合并总量都符合 1–99 后：

- 没有匹配项：插入一行；
- 有匹配项：保留第一行，调用 `updateSnapshot` 写入新总数及服务器重新构建的快照；
- 有多条旧重复项：删除第一条以外的重复行。

所以它不仅判断匹配，还能修复旧数据里已经存在的完全相同 SKU 重复行。

## 5. 一组输入的新旧结果对比

假设购物车里有：

| 购物车行 | 菜品 ID | 口味 | 数量 |
| --- | ---: | --- | ---: |
| A | 7 | `大份,少辣` | 2 |
| B | 7 | 空字符串 | 1 |
| C | 8 | 空字符串 | 3 |

请求是“菜品 7，无口味，再加 1 份”，但序列化后口味为 `null`：

| 实现 | 结果 |
| --- | --- |
| 旧动态查询 | 忽略口味条件，A、B 都是候选；取决于排序，只改第一行，可能错误增加 A |
| 当前实现 | `identity` 将 null 规范化为空字符串；`same` 要求 dishId=7、setmealId=null、口味为空；只匹配 B，数量由 1 变 2 |

若请求要减“菜品 7，无口味”，同理只会减 B，不会动 A。菜品 8 即使也无口味，因为菜品 ID 不同也不会匹配。

## 6. 新旧逻辑优缺点

| 方面 | 旧逻辑：动态 SQL 条件查询 | 当前逻辑：用户列表 + `same` |
| --- | --- | --- |
| 口味为 `null` | `<if>` 省略口味条件，可能匹配同菜品的其他口味 | `null` 归一为空字符串，精确匹配无口味项 |
| SKU 身份规则 | 隐含在 DTO 哪些字段非空中，缺少统一校验 | 集中定义为菜品/套餐身份 + 口味，入口先验证 |
| 减购精度 | 结果可能有多行，只取第一行 | 在用户范围内按完整身份找匹配行 |
| 旧重复行 | 只处理第一条，剩余重复项保留 | 加购时合计完全匹配行并清理额外重复项 |
| 更新商品快照 | 命中旧行时只加数量，快照可能陈旧 | 加购先重建当前商品快照，合并时一并更新 |
| 查询成本 | SQL 条件较细，数据库可能只返回匹配项 | 每次先取该用户的购物车，再在 Java 逐条比较，购物车越大成本越高 |
| 并发写 | 旧入口没有统一用户锁，可能丢增量或重复插入 | 当前写入口先锁同一用户行，并在事务中完成查询与修改 |
| 数据库约束 | 动态匹配本身不解决并发重复行 | 仍没有 SKU 唯一索引；正确性依赖写入口遵守用户锁约定 |

## 7. 当前做法的优点与代价

### 优点

1. **身份规则在 Java 中统一。**加购、减购、再来一单复用同一比较语义，不再依赖请求字段是否为 `null` 来隐式决定 SKU。
2. **无口味处理稳定。**数据库中存空字符串时，客户端传 `null` 或空字符串都被视为无口味。
3. **先把数据限定到当前用户。**比较只发生在该用户购物车行内，用户 ID 不由客户端指定。
4. **复杂业务更容易扩展和测试。**若以后 SKU 身份要加入规格编码，调整 `same` 并更新相关校验，比散落在 Mapper 动态条件和多个 Service 中更集中。
5. **合并时能收敛已有重复行。**精确相同的旧行会归并数量并删除多余记录。

### 代价和限制

1. **数据库返回行数更多。**加购和减购按 userId 取整个购物车，再由 Java 比较。个人购物车规模通常不大，逻辑直观；若购物车可非常大，旧式的精确 SQL 过滤更省网络与内存，可以把相同语义下推到 SQL，或使用规范化 SKU key/索引。
2. **仍依赖用户锁协议。**当前代码通过 `UserWriteLock` 让这些写请求排队，但数据库没有 SKU 唯一约束。任何绕过锁的写入口仍可能造成并发重复行。
3. **口味字符串是精确字符串比较。**当前 `same` 只统一 null/空串，不会拆分后排序或做语义规范化。因此 `"大份,少辣"` 与 `"少辣,大份"` 会被视为不同 SKU。项目靠规格组稳定顺序和调用方使用同一编码顺序来匹配；如果前端可能乱序，应进一步在服务端按规格组 canonicalize 后再存储和比较。
4. **查询结果的旧数据清理只覆盖精确相同的表示。**null 与空串会等同；口味项顺序不同或格式不一致的字符串不会自动合并。
5. **SKU 的字段范围要同步演进。**如果未来菜品出现尺寸 ID、加料项、套餐选项等新维度，仅比较当前三个字段就不足以区分 SKU，必须同步更新实体、请求结构、存储、比较和测试。

## 8. 什么时候考虑把匹配下推到 SQL

当前做法优先保证身份语义集中、无口味明确、可复用。若用户购物车行数增长导致读取整张个人购物车成为性能瓶颈，可以考虑改为 Mapper 提供一个明确的精确查询，例如以 `user_id`、`dish_id`/`setmeal_id` 和规范化 `dish_flavor` 查找；需要特别处理 NULL/空字符串统一和菜品/套餐互斥条件。SQL 查询与 Java 的 `same` 规则必须完全一致，否则又会出现“加购按一种规则匹配、减购按另一种规则匹配”的问题。

同时，可以评估将口味编码为结构化 SKU 字段或生成规范化 SKU key，并建立用户范围内的唯一约束。但加唯一约束前必须清理历史重复数据；应用仍应处理唯一冲突。用户行锁和唯一约束是不同层次的保护：前者协调遵循协议的业务写流程，后者在数据库层拒绝重复身份记录。

## 总结

旧逻辑把 DTO 转成动态查询条件，代码短且查询候选少，但“字段为 null 就不筛选”会把“缺省字段”和“精确无口味”混在一起，可能误加或误减其他口味 SKU。当前逻辑先验证 SKU 身份、把 null 口味规范成空串，再限定当前用户购物车并用统一的 `same` 比较完整身份；好处是规则清楚、加减口径一致、还能归并旧重复项。代价是每次操作会读取该用户整份购物车，而且字符串口味比较依赖稳定顺序，数据库唯一约束仍未替代应用锁。
