# 购物车相关新增代码详解

整理日期：2026-09-24。

本文结合当前后端代码，说明小程序重构中购物车相关的新增和调整：购物车怎样认定商品、怎样合并数量、如何校验价格和规格、怎样处理并发，以及下单和“再来一单”怎样复用购物车逻辑。

涉及的主要文件：

- [ShoppingCartServiceImpl.java](../sky-server/src/main/java/com/sky/service/impl/ShoppingCartServiceImpl.java)：加购、减购、查看、清空和购物车合并。
- [CartRules.java](../sky-server/src/main/java/com/sky/service/support/CartRules.java)：统一校验商品身份、销售状态、口味规格、价格和数量。
- [UserWriteLock.java](../sky-server/src/main/java/com/sky/service/support/UserWriteLock.java)：相关写流程取得当前用户行锁。
- [ShoppingCartMapper.java](../sky-server/src/main/java/com/sky/mapper/ShoppingCartMapper.java)：购物车数据库操作，包括新增的快照更新 SQL。
- [ShoppingCartMapper.xml](../sky-server/src/main/resources/mapper/ShoppingCartMapper.xml)：按用户、菜品/套餐和口味查询购物车。
- [UserOrderService.java](../sky-server/src/main/java/com/sky/service/UserOrderService.java)：下单时核价并消费购物车；再来一单时重建并合并购物车。

## 1. 先看购物车里一行数据代表什么

购物车表的一行不是单纯的“菜品 ID”，它代表用户选择的一种具体 SKU（可购买项）：

```text
用户 + 菜品 ID 或套餐 ID + 菜品口味 = 一个购物车项
```

例如：

```text
用户 18，菜品 7，口味“大份,少辣”   → SKU A
用户 18，菜品 7，口味“小份,少辣”   → SKU B
用户 18，套餐 3，无口味             → SKU C
```

同一道菜不同口味不能合成一行。套餐和菜品也不能混为同一个商品。`CartRules.same(a, b)` 就是以 `dishId`、`setmealId`、`dishFlavor` 三项比较两行是否为同一个 SKU；`null` 口味与空字符串都按“无口味”处理。

## 2. 加购：先锁用户，再由服务器组装商品数据

当前 `addShoppingCart` 的主要顺序如下：

```text
@Transactional
  1. userWriteLock.lock()       当前用户写流程排队
  2. rules.requireOpen()        检查店铺营业状态
  3. DTO 复制成购物车对象       只把请求字段作为选择信息
  4. 设置 userId                用户归属取自登录上下文，不信任客户端
  5. rules.hydrate(row)         查当前菜品/套餐，验证规格并填充当前名称、图片、价格
  6. merge(row, 1)              数量 +1，或插入购物车行
```

整个入口是 `@Transactional`。同一用户的其他购物车写操作也先取得用户行锁，所以并发加购和下单等流程会依序处理。

### 为什么不能直接相信 DTO 的金额和名称

请求 DTO 来自客户端。用户可以改请求中的 `amount`、`name`、`image` 等字段；这些字段不能决定最后价格。加购时 `hydrate` 根据数据库中的当前商品重建购物车快照：

- 菜品：查菜品是否存在、是否在售；加载规格组；验证请求选择的每组规格都仍有效；将菜品当前名称、图片、价格写入对象。
- 套餐：查套餐是否存在、是否在售；不允许带菜品口味；将套餐当前名称、图片、价格写入对象。
- 价格为空或小于 0 时拒绝加入。

这里的名称、图片、金额是购物车保存的展示/历史快照；下单时仍会重新查当前商品并核价，不把购物车快照当作最终价格依据。

## 3. `CartRules`：把重复业务规则集中起来

### `identity(row)`：商品身份必须明确

它要求菜品 ID 和套餐 ID 必须且只能提供一个：

```text
dishId 有值，setmealId 为空   ✓
dishId 为空，setmealId 有值   ✓
dishId 和 setmealId 都为空   ✗
两者都有值                     ✗
```

ID 还必须为正数。口味字段若为 `null`，会规范化成空字符串。这样后面的比较和 SQL 对“无口味”有一致表示。

### `hydrate(row)`：用当前商品信息验证、填充

这个方法的名字可理解为“把选择重新装配为一份当前有效的商品快照”。它除了填充名称、图片、金额，还检查商品是否仍存在、是否在售、规格是否仍有效。它被加购、下单和再来一单调用，避免三个入口各自写出不同的售卖规则。

对菜品口味，代码取该菜品的规格组，要求请求中选择的口味项数量与规格组数量一致，再逐组验证选择在可选列表里。规格组查询按 ID 排序，使口味字符串的项目顺序稳定。若商品规格配置已改，旧购物车/旧订单里的选择就会被拒绝，需要用户重新选择。

### `quantity(n)`：数量边界统一

每种 SKU 数量为 1 至 99。该规则会在加入、合并、减购校验现存行以及下单中使用。合并后也再次检查总数，防止通过多次添加超过上限。

### `requireOpen()`：检查店铺营业状态

加购、下单和再来一单会要求店铺营业。减购没有调用此方法，所以即使店铺休息，用户仍可以从购物车移除商品；清空也允许执行。这是合理的体验规则：休息时不接受新购买，但应允许用户整理或清空购物车。

## 4. `merge(row, quantity)`：合并相同 SKU

`merge` 先查询该用户全部购物车行，再用 `rules.same` 筛出相同 SKU。之后：

1. 检查这次增加的数量合法。
2. 检查已有匹配行的数量合法。
3. 计算已有数量总和加本次数量，并检查合并后的数量仍不超过 99。
4. 没有匹配行：设置创建时间并插入新行。
5. 找到匹配行：保留第一条，将其 ID 放到新对象上，通过 `updateSnapshot` 更新数量、当前名称/图片/金额/口味；若旧数据里已有多条重复 SKU，则删除其余重复行。

举例：购物车里已有“牛肉面、大碗、少辣”两行，数量分别 2 和 1。再次加入同样选择 1 份时，代码会把匹配数量归并为 4，更新保留行，并删除多余重复行。若加入“牛肉面、小碗、少辣”，口味字符串不同，是另一个 SKU，不能合并。

`merge` 的注释明确要求调用者已在事务中锁定用户。普通加购由 `addShoppingCart` 先拿锁；“再来一单”也先锁用户，再调用 `merge`。这样合并过程不是一个漏掉并发保护的公共写入口。

## 5. 新增 `updateSnapshot`：按行主键和用户归属更新

Mapper 新增 SQL：

```sql
UPDATE shopping_cart
SET number = ?, amount = ?, name = ?, image = ?, dish_flavor = ?
WHERE id = ? AND user_id = ?;
```

它做两件事：

- 更新购物车数量和商品快照，保持同 SKU 合并后信息是本次按当前菜品/套餐重新核验得到的值。
- `WHERE` 同时要求 `id` 和 `user_id` 匹配，避免仅凭购物车行 ID 更新不属于当前用户的记录。

`updateSnapshot` 不是“下单时更新购物车价格”的操作。下单流程会把购物车消费并删除；此更新主要服务于加购/再来一单的合并。

## 6. 减购：按完整 SKU 精确找到一行

`subShoppingCart` 的流程是：

1. 开启事务并锁当前用户。
2. 将 DTO 变成查找 key，调用 `rules.identity` 规范化菜品/套餐 ID 和口味。
3. 查询该用户的购物车行。
4. 用 `rules.same` 找到完整匹配项。
5. 数量为 1：删除该购物车行；数量大于 1：减一并更新数量；完成后返回。

这里不会重新校验商品是否在售，因此下架商品仍能减掉或删除。按完整 SKU 匹配也避免“减无口味菜时误减有口味菜”。更新或删除只作用于找到的用户购物车行；对应的服务写入口先持用户锁。

找不到匹配 SKU 时，当前方法不做更改，也不抛“商品不存在”错误。这让重复点击减购或行已被移除时保持无副作用。

## 7. 查看和清空

### 查看 `showShoppingCart`

查看是普通读取：用 `BaseContext.getCurrentId()` 取用户 ID，再按 `user_id` 查询。它没有拿写锁，因为读取购物车不负责改变数据，也不应该让所有查看请求和同用户写操作都排队。并发期间读到哪个已提交版本取决于数据库事务时机。

### 清空 `cleanShoppingCart`

清空是写操作，所以加了 `@Transactional` 并先调用 `userWriteLock.lock()`，再按返回的用户 ID 执行 `deleteByUserId`。这使清空和加购、下单共享排队规则，避免一边清空一边同时加入/消费购物车而造成难以解释的结果。

## 8. 下单：重新核价，写单据后消费购物车

`UserOrderService.submit` 不是直接相信购物车里存的金额。其顺序是：

```text
@Transactional
  → 锁当前用户
  → 检查营业状态和下单参数
  → 查该用户购物车
  → 对每行检查数量，并用 hydrate 查最新商品/规格/价格
  → 用当前价格 × 数量计算商品金额
  → 创建订单和订单明细
  → 按 userId 删除购物车
  → 提交
```

因此购物车里的快照主要用于页面展示；真正的下单金额取自服务器当前商品记录。订单明细从已经 `hydrate` 的购物车对象复制，记录的是本次下单核价时的名称、图片、规格、价格和数量。若中途创建订单明细等步骤失败，事务会回滚，购物车删除也一并回滚。

同用户两个下单请求会在用户行锁处排队。第一个成功提交并清空购物车后，第二个才继续查车，通常会发现购物车为空，而不会再拿同一份购物车创建第二张订单。

## 9. 再来一单：重建商品、保留现有购物车并合并

“再来一单”不会把旧订单价格直接复制进购物车。它会：

1. 在事务中锁当前用户，并确认旧订单归当前用户。
2. 读取旧订单明细。
3. 将明细转换成购物车对象，设置当前用户 ID。
4. 校验数量，并用 `hydrate` 按当前商品状态、规格、名称和价格重建每一行。
5. **先全部验证，再逐行合并**到当前购物车。

若旧订单里的某道菜已下架、规格失效或合并数量超过 99，会在合并前失败；事务回滚，不会只加进去一半，也会保留用户原购物车。全部有效时，相同 SKU 数量累加，不同口味保留为不同项。

## 10. 相较旧实现的主要变化

| 方面 | 旧逻辑的主要做法 | 当前逻辑 |
| --- | --- | --- |
| 当前用户 | 直接读取 `BaseContext` | 写操作通过 `UserWriteLock` 取得用户行锁，再使用返回 ID |
| 加购商品数据 | 仅在新插入时查菜品/套餐；已有项直接数量加一 | 无论插入还是合并，先按数据库当前商品重建并校验快照 |
| SKU 匹配 | mapper 按 DTO 动态字段查，口味条件容易缺省/不精确 | 读取该用户购物车，按菜品/套餐 ID 与规范化口味精确比较 |
| 重复购物车行 | 更新查询结果中的第一条，未归并旧重复行 | 合并数量，更新保留行，清理额外重复 SKU |
| 数量 | 原有加一/减一逻辑较简单 | 统一检查每项和合并结果的 1–99 范围 |
| 商品有效性 | 购物车阶段校验较少 | 共用规则校验上下架、规格、套餐口味与价格；下单再次核价 |
| 更新归属 | 旧数量更新主要按行 ID | 新的快照更新同时带 `id` 与 `user_id` 条件 |
| 下单并发 | 多步写入未共享购物车写操作锁 | 下单、购物车写入口用同一用户行锁，并在事务中消费购物车 |

## 11. 阅读代码时要记住的几个边界

- 购物车金额是展示快照，不是最终结算凭据；下单会重新查价。
- `UserWriteLock` 锁的是用户表的一行，不是直接锁住购物车表；效果依赖所有相关写入口遵守同一加锁协议。
- `showShoppingCart` 是普通读取，不会取得写锁；这与加购、减购、清空的写锁策略不同。
- `rules.hydrate` 是校验和构造当前快照，不是写数据库；合并时 mapper 更新购物车快照，下单时订单明细使用它并随后删除购物车。
- “再来一单”是往现有购物车追加/合并，不是先清空购物车再重建。

## 总结

这组购物车代码的核心思路是：用 `CartRules` 保证菜品/套餐、规格、价格与数量规则一致；用 `UserWriteLock` 让同一用户的购物车写操作和下单排队；用事务保证合并、订单及购物车消费中的数据库改动保持完整；用精确 SKU 比较防止不同口味混在一起；并在下单时从服务器商品数据重新核价。这样购物车不再只是“把客户端提交的字段存起来”，而成为经过服务器校验、可以安全用于后续下单的商品选择集合。
