## 一、这次到底改了什么

核心目标不是换一套后端框架，而是让新小程序能够安全、准确地使用原有接口，尤其解决四类问题：**数据归谁、金额谁算、重复操作怎么办、订单状态能不能被错误覆盖。**

| 原来存在的问题 | 此次处理 | 用户能感受到的结果 |
| --- | --- | --- |
| 下单对象复制了前端传来的金额 | 根据当前服务器商品价格和购物车数量重新算钱 | 修改请求中的金额不能得到低价订单 |
| 一些地址、订单操作只按 ID 查询 | 校验记录所属用户与当前登录用户一致 | 不能仅靠换一个 ID 操作别人的记录 |
| 下单与购物车修改之间存在并发窗口 | 同用户写入先锁 user 行；下单事务内消费购物车 | 同一批购物车不会同时生成两份订单 |
| 支付、取消、接单、定时任务普通更新会相互覆盖 | SQL 带上“预期旧状态”条件，检查影响行数 | 已取消订单不会被旧支付请求重新变成待接单 |
| 无口味请求可能忽略口味条件 | SKU 精确比较，null 与空串统一代表无口味 | 无口味商品不会误减某个有口味的商品 |
| 再来一单直接复制旧价格、直接插入新行 | 按当前商品信息重建，追加并合并到现有购物车 | 保留原有商品，相同规格数量合并 |
| 地址编辑没有更新地区字段；订单地址不完整 | 更新省市区代码/名称；保存完整地址快照 | 返回编辑页能回显地区，订单保留当时地址 |
| 模拟支付缺少有效期和状态约束 | 当前用户、未支付、15 分钟有效期、条件更新 | 模拟支付也遵守订单规则，不随意改成已支付 |
| 日志打印 token、微信会话或 OSS 凭证对象 | 删除相应敏感日志 | 减少凭证通过日志泄露的风险 |
| 表情备注触发数据库字符错误并返回 500 | 识别特定字符错误，明确提示；原事务回滚 | 知道需要修改输入，购物车不丢失 |

这些修改仍使用原来的 **Spring Boot + MyBatis + MySQL + Redis**。没有引入新的业务接口，没有迁移到 JPA，没有改数据库表结构，也没有接入真实扣款或真实退款。

## 二、先理解几个必要概念

### 1. Controller、Service、Mapper 分别做什么

可以把后端看成一个餐厅：Controller 是接单窗口，Service 是处理规则的负责人，Mapper 是实际登记账本的人。

```text
小程序 HTTP 请求
    ↓
JwtTokenUserInterceptor：验证身份，把当前用户 ID 放入上下文
    ↓
Controller：接收参数，调用业务服务，返回 Result
    ↓
Service：判断权限、价格、数量、状态；组织事务
    ↓
Mapper / XML：执行数据库查询、插入、更新、删除
    ↓
MySQL：保存最终数据
```

营业状态仍从原有店铺状态服务获取；微信登录和 Redis 相关基本架构没有被重新设计。

### 2. 认证不等于授权

**认证**回答“你是谁”：token 有效，知道你是用户 A。

**授权**回答“这条数据能不能给你”：即使 A 已登录，也不能读取 B 的订单。

因此，JWT 校验成功以后，Service 仍然要比较 `record.userId` 与 `BaseContext.getCurrentId()`。ID 不难猜、前端隐藏按钮，都不能代替这一步。

### 3. 事务不等于防止所有并发

事务可以让“创建订单、创建明细、清空购物车”一起成功或一起回滚。但两个事务仍可能同时读取同一份购物车。因此本次还增加了用户行锁，让同一用户的相关写入排队。

### 4. 行锁和条件更新解决的问题不同

| 机制 | 本项目用途 | 通俗理解 |
| --- | --- | --- |
| `SELECT ... FOR UPDATE` | 同一用户购物车、下单、再来一单、地址写入 | 一个用户的这一组写操作先排队，再处理 |
| `UPDATE ... WHERE status = 预期值` | 支付、取消、接单、配送、定时任务 | 修改前再确认状态还是刚才看到的样子，否则不能覆盖 |
| `@Transactional` | 多条数据库操作组成一个整体 | 中间失败时撤销这次事务已经做的数据库修改 |

三者互补，不是任选一个就能解决所有问题。

### 5. DTO、实体、VO

DTO 是“请求带来的参数”；实体通常对应数据库记录；VO 是“返回给前端的数据”。`BeanUtils.copyProperties` 只是同名属性复制，不会替你判断价格可信、记录归属或状态合法。

此次一个重要变化就是：复制 DTO 时明确排除不能直接信任的字段，再由后端生成它们。

## 四、订单服务为什么拆开

### 1. 修改前：不同身份的逻辑挤在一起

旧 `OrderServiceImpl` 同时承接用户下单、支付、取消、再来一单，以及商家查询、接单、拒单和配送。

如果直接给共享 `details(id)` 加“订单必须属于当前用户”，管理端也会受到影响：管理端上下文里是员工身份，不能拿员工 ID 去比较消费者 ID。

### 2. 修改后：先区分入口身份，再复用查询

```text
用户 /user/order/orderDetail/{id}
    → UserOrderService.detail(id)
    → owned(id)：必须属于当前消费者
    → OrderService.details(id)：组装订单和明细

商家 /admin/order/details/{id}
    → OrderService.details(id)
    → 按管理端原有登录权限访问，不套消费者归属条件
```

这不是取消了商家鉴权，而是没有把“消费者只能看自己的订单”错误套用到商家查询里。用户新接口必须走专用入口，不能绕回共享 details。

### 3. 原方法迁到了哪里

| 原 OrderService 方法 | 现在的位置 |
| --- | --- |
| `submitOrder(dto)` | `UserOrderService.submit(dto)` |
| `payment(dto)` + `paySuccess(orderNumber)` | 合并到 `UserOrderService.payment(dto)` 中，事务内处理 |
| `userCancelById(id)` | `UserOrderService.cancel(id)` |
| `repetition(id)` | `UserOrderService.repeat(id)` |
| `reminder(id)` | `UserOrderService.remind(id)` |
| 用户调用 `details(id)` | 改为先调用 `UserOrderService.detail(id)` |
| `pageQuery4User(...)`、商家查询/统计/状态操作 | 保留在 OrderService / OrderServiceImpl |

HTTP 接口路径与请求方法没有随 Java 方法名变化。当前源码调用方已同步迁移；如果你另外写了未包含在本工程的 Java 调用方，则需要按这张表调整。

### 4. 为什么用了 final 和 RequiredArgsConstructor

新服务和重写的主要服务使用 `private final` 字段配合 Lombok 的 `@RequiredArgsConstructor`。Lombok 生成带必需依赖的构造器，Spring 创建服务时传入 Mapper 和其他服务。

好处是依赖一眼可见，测试可以直接 `new UserOrderService(mock1, mock2, ...)`。这是本次采用的 java-springboot 技能规范之一；没有顺便把全工程所有旧 `@Autowired` 类都重写。

## 五、地址与用户身份如何保护

### 1. 列表与单条记录都要限制

地址列表 `list(filter)` 会把 userId 强制设为 `BaseContext.getCurrentId()`，不采信客户端传来的 userId。

单条地址的 `getById(id)` 查询后执行：

```java
if (row == null || !Objects.equals(row.getUserId(), BaseContext.getCurrentId())) {
    throw new AddressBookBusinessException("地址不存在或无权访问");
}
```

`Objects.equals` 可以处理空值，避免直接对可能为 null 的对象调用 equals。对“不存在”和“属于别人”使用同一种提示，不通过不同提示帮助用户猜测别人的记录是否存在。

编辑、删除、设默认、下单选址均调用受保护的查询。订单也有对应的 `owned(id)`，供用户详情、取消、再来一单和催单使用。

### 2. 默认地址为什么先校验、再清旧默认

正确顺序：

1. 进入事务并锁当前用户行。
2. 确认目标地址存在且属于当前用户。
3. 把当前用户的地址设为非默认。
4. 把已校验的目标地址设为默认。

如果先执行第 3 步再发现目标地址无权访问，就容易产生错误的中间行为。当前顺序加事务避免越权操作影响自己的默认地址；两次同时设默认也通过同一用户锁排队。

没有默认地址时返回 `code=1, data=null`，含义是“查询成功，确实没有默认地址”，不是网络或系统异常。新前端据此允许用户手动选一个地址。

### 3. 新增、编辑、删除各自做了什么

| 方法 | 保护规则 |
| --- | --- |
| `save` | 当前用户 ID 来自登录上下文；忽略客户端 id；新地址默认 isDefault=0；校验字段 |
| `update` | 校验旧记录归属；固定为旧 userId；忽略客户端默认标记；保留旧 sex；更新其他允许字段 |
| `setDefault` | 先校验目标，再重置同用户默认，最后设目标默认 |
| `deleteById` | 先锁当前用户、检查目标归属，再删除 |

具体字段校验是：联系人有内容且最多 32 个 Java 字符单位；手机号匹配 `1[0-9]{10}`；省/市/区名称和详细地址非空；详细地址最多 120 个字符单位，标签最多 16 个字符单位。

这不代表已经验证手机号真实存在或行政区代码真实有效。地区代码已补齐持久化，但没有另建完整行政区数据库做真实性校验。

### 4. XML 为什么也要加 user_id

编辑 SQL 现在包含：

```sql
where id = #{id} and user_id = #{userId}
```

服务层先检查业务权限，SQL 再限定更新范围，属于双层约束。六个地区字段分别通过 `<if>` 更新：province/city/district 的 code 和 name。MyBatis `<set>` 会整理动态 SET 片段，`#{...}` 通过参数绑定传值。

删除地址的旧 Mapper SQL 本身仍按 id 删除；当前安全性来自进入它之前的归属校验和共同锁。不要以后从一个未检查归属的新入口直接调用它。

## 六、下单：重新核价、事务和并发锁

这一节对应新增 `UserOrderService.submit`，是此次修改的核心。

### 1. 以前的问题

以前将 DTO 的同名属性复制到订单时，金额也会随之复制；购物车查询、订单插入与清空之间也没有共同用户锁来阻止重复消费同一批购物车。

客户端请求不是可信账单。即使按钮显示 79 元，调用者仍可以把请求体 amount 改成 0.01。后端必须自行确认价格与数量。

### 2. 现在 submit 的完整执行顺序

```text
开始事务
  → 从 token 上下文获取用户，锁定 user 行
  → 检查营业状态、DTO 参数
  → 查当前用户拥有的地址
  → 查当前用户购物车，空则拒绝
  → 每行检查数量、商品可售、口味有效；重新取当前价格
  → 计算总价、包装费、餐具数量
  → 生成订单编号、时间、初始状态、地址快照
  → 插入订单，取得数据库生成的订单 ID
  → 插入明细，并关联新订单 ID
  → 清空当前购物车
提交事务 → 返回实际订单 ID、编号、金额和时间
```

任何参与事务的数据库步骤失败，RuntimeException 会让本次数据库事务回滚。这里的 BaseException 继承 RuntimeException，符合 Spring 默认的运行时异常回滚规则。

### 3. 价格的来源与公式

```text
商品金额 = Σ（当前商品单价 × 购物车该行数量）
包装费   = 总件数 × 每件包装费
订单金额 = 商品金额 + 包装费 + 配送费
```

例如一份 72 元的菜：`72 + 1 + 6 = 79 元`。

六份相同的菜：`72 × 6 + 1 × 6 + 6 = 444 元`。包装费按件，不是“购物车一行就收一元”；配送费按本次订单一次收取。

关键代码：

```java
BeanUtils.copyProperties(dto, order, "amount", "packAmount", "tablewareNumber");
order.setAmount(goods.add(BigDecimal.valueOf((long) count * packFeePerItem)).add(deliveryFee));
order.setPackAmount(count * packFeePerItem);
```

第一行把不可信金额字段排除；后两行使用服务端核算结果。即便数据库购物车保存的是旧价格，`rules.hydrate(row)` 也会在下单时重新取得当前商品价格。订单明细保存这次核价后的快照，不再随以后商品改价而变动。

`BigDecimal` 用于金额十进制计算。配置默认值通过字符串建立 BigDecimal，避免直接把二进制浮点误差当成价格。

### 4. 还校验了哪些下单参数

| 参数 | 当前规则 |
| --- | --- |
| 地址 | 必填，存在且属于当前用户 |
| `payMethod` | 只接受 1，即本轮微信渠道演示支付 |
| `deliveryStatus` | 0 为预约，1 为立即配送 |
| 预约时间 | 至少当前时间一小时后；今天或明天；09:00—23:00；分钟为0或30；秒为0 |
| 立即配送时间 | 服务端填当前时间后一小时，属于演示约定，不是实时运力预测 |
| `tablewareStatus` | 1 按餐量；0 使用指定数量 |
| `tablewareNumber` | 未提供先设0；显式传入需0—99；按餐量时最终由商品总件数生成 |
| 备注 | 最多100个Unicode码点；与数据库是否支持表情是两层限制 |
| 数量 | 每行/合并规格1—99件；整单总件数不超过999 |

按餐量时最终餐具数可能大于99，因为它由整单件数推导；0—99校验针对输入的指定数量，不应误写成所有情况下最终餐具数都不超过99。

### 5. 为什么锁 user，而不是只锁购物车

新增 SQL：

```sql
select id from user where id = #{id} for update
```

当前用户行稳定存在，购物车却可能为空。如果只试图锁“已经存在的购物车行”，新增购物车和清空后的并发就更难统一处理。

`UserWriteLock.lock()` 负责取当前用户并调用 SQL；真正的锁持续时间由外层事务控制。所有相关入口约定先锁同一个用户行，购物车新增/减少/清空、下单、再来一单、地址写入才会彼此协调。

假设 A、B 同时提交同一份购物车：

| 时刻 | 请求 A | 请求 B |
| --- | --- | --- |
| 1 | 取得当前用户行锁 | 等待同一个用户行锁 |
| 2 | 查到购物车，创建订单及明细 | 继续等待 |
| 3 | 清购物车并提交，释放锁 | 取得锁 |
| 4 | 返回成功 | 再查发现购物车为空，拒绝重复下单 |

不同用户锁不同的行，不是把全站所有订单排成一队。多 Java 实例使用同一 MySQL、同样遵守锁协议时也能协调，但本次没有做多实例部署压力测试。

### 6. 事务使用上的两个重要前提

`UserWriteLock` 自身没有新建一层事务，它必须由已进入事务的业务方法调用。没有事务时，锁可能很快释放，达不到保护整段逻辑的效果。

`ShoppingCartServiceImpl.merge` 同样要求调用者已取得用户锁并处于事务中。它是复用片段，不是可以独立暴露给 Controller 的任意写入口。Spring 事务依赖代理调用；今后新增方法时还要注意同类内部调用不会自动建立新的代理事务边界。

### 7. 订单编号、明细与地址快照

订单 number 从时间戳字符串改成去掉连字符的 UUID，得到32位字符串，降低同时下单的编号碰撞风险。它不是数据库主键 id；前端不能再假设订单编号一定全是十进制数字。

购物车转订单明细时明确不复制 `id`，再设置新的 `orderId`。两个表的记录身份不应混用。原订单明细 insert 本来就没有插入 id 列，所以这是明确的对象边界保护，不能夸大成“之前每次都会因主键冲突失败”。

地址现在保存省名+市名+区名+详细地址，并保存联系人和电话。这是下单时的快照：用户后来编辑地址簿，不应改变已经下的订单。历史订单没有批量补齐；直辖市省市名称可能出现重复文字，当前是兼容结构的直接拼接，并非完整地址格式化系统。

## 七、购物车与规格怎样处理

### 1. 先搞清楚 SKU 的含义

本项目可以把 SKU 理解成“一种确切的商品选择”：同一道菜的微辣和特辣是两种选择，应当在购物车分成两行。

当前比较键是：

```text
dishId + setmealId + dishFlavor
```

dishId 与 setmealId 必须有且只有一个不为空。两个都填和两个都不填都拒绝；存在的 ID 还必须大于0。无口味的 null 被规范成空字符串，但空字符串不会匹配到“微辣”。

### 2. CartRules 每个方法的职责

| 方法 | 具体工作 |
| --- | --- |
| `requireOpen()` | 调用原营业状态服务，只有1允许新增点餐 |
| `identity(row)` | 商品类型二选一、正 ID、口味空值规范化 |
| `hydrate(row)` | 查询当前菜品/套餐，检查在售、验证口味，从数据库填名称/图片/价格，拒绝空或负价格 |
| `same(a,b)` | 比较两个商品 ID 和规范化后的口味，判断是不是相同 SKU |
| `quantity(n)` | 数量必须非空、1—99 |

`hydrate` 可以理解成“把只知道商品编号的记录，用当前可信的商品资料补完整”。它不是继续相信客户端或旧订单里的名称与价格。

套餐检查的是套餐记录本身存在且在售；当前没有额外新增“逐一锁定套餐内所有菜品”的机制。

### 3. 规格顺序为什么要固定

菜品规格是多个分组，每组 value 是 JSON 字符串，例如：

```text
分组1 辣度：[微辣, 特辣]
分组2 温度：[常温, 热]
选择串：微辣,热
```

后端按顺序拆串，要求组数一致、每个值属于对应组选项。`DishFlavorMapper` 增加 `order by id`，让前端展示顺序与后端校验顺序一致。

仍保留旧接口逗号分隔格式，没有设计转义协议。因此规格选项自身不宜含英文逗号，否则会被拆成多个选项。这是兼容旧结构的边界，不是通用的任意字符串规格编码。

### 4. 加购和历史重复行如何合并

`addShoppingCart` 先锁用户、检查营业、重建当前商品资料，再调用 `merge(row,1)`。

merge 读取本用户购物车，筛出完全相同 SKU：没有则插入；有则把原来所有相同 SKU 数量加起来再加本次数量，保留第一条记录并更新快照，删除其余重复行。

例如旧数据有相同 SKU 的2件和3件两行，现在再加1件，结果为一行6件，价格也更新为当前价格。如果合并超过99件，整个操作失败，不会静默截成99。

`updateSnapshot` 不只更新 number，还更新 name、image、amount、dishFlavor，并带 `id + user_id` 条件。数据库没有新增 SKU 唯一索引，因此并发保护仍依赖这些写入口一致执行用户锁。

### 5. 减购、清空为什么没有要求营业

关闭营业或商品下架后，用户仍应能把旧商品从购物车移除。因此减购只验证标识和匹配行数量，不强制商品当前可售。数量1时删除，否则减1；没匹配到就不修改。

减购当前只处理匹配到的一行，不会顺便把所有历史重复行整理一遍；加购/再来一单的 merge 才做归并。清空使用当前用户 ID 并同样先锁用户，不影响别人的购物车。

## 八、模拟支付、取消与订单状态

### 1. 两种状态不能混为一谈

| 字段 | 值与含义 |
| --- | --- |
| `status` | 1待付款、2待接单、3已接单、4派送中、5已完成、6已取消 |
| `payStatus` | 0未支付、1已支付、2已退款 |

取消未付款订单通常是 `status=6,payStatus=0`；取消已付款订单则是 `status=6,payStatus=2`。不存在本次自定义的“订单状态7等于退款”。本项目的已付/已退款都是模拟状态。

### 2. 支付现在怎么执行

`UserOrderService.payment` 依次做以下检查：

1. payMethod 必须为1。
2. 用订单号与当前用户 ID 联合查询，找不到就拒绝。
3. 若已付且订单仍处于2—5，返回兼容的空支付 VO，不重复更新或通知。
4. 新支付必须是待付款、未支付，且下单时间加15分钟仍晚于当前时间。
5. 调用 `payIfPending`，要求恰好更新1行；否则提示刷新状态。
6. 注册事务提交后的商家来单通知。

原来 Controller 调一次 payment，再单独调 paySuccess 的两步被合并，避免 Controller 持有业务状态变更细节。

### 3. 为什么 Java 判断后还要 SQL 判断

精简后的关键 SQL：

```sql
update orders
set status = 2, pay_status = 1, checkout_time = #{now}, pay_method = 1
where id = #{id}
  and user_id = #{userId}
  and status = 1
  and pay_status = 0
  and timestampadd(MINUTE, 15, order_time) > #{now}
```

Java 查询与 SQL 更新之间，另一个请求可能取消了订单。SQL 再次要求 status=1，才能阻止已取消订单被覆盖。

返回影响行数1表示当前条件成立并完成修改；0表示不满足条件，不能当成成功。这个方法的有效期比较使用本次调用传入的 now，来源是 Java 服务时间，不是数据库服务器直接生成的时钟。

### 4. 通用条件更新 updateExpected

OrderMapper.xml 中的新方法通过动态 `<set>` 只修改非空字段，最后统一增加：

```sql
where id = #{order.id} and status = #{expectedStatus}
```

调用方必须先做该入口的归属/业务校验。这个通用方法没有 user_id 条件，因为商家和定时任务也要使用；不能把它本身当成授权机制。

旧 Mapper.update 没有被全工程删除，但本次受保护的订单状态迁移已改走新方法。以后新增状态操作时，若又用普通 update 覆盖状态，会重新引入竞争风险。

### 5. 用户取消规则

只允许状态1和2。状态3以后商家已接单，用户不能直接取消。取消填写取消原因、取消时间；当前已支付就设为模拟退款，否则仍未支付。UPDATE 要求数据库旧状态等于刚才读到的状态。

### 6. 支付与取消同时来，究竟谁成功

要区分两种情况：

| 情况 | 结果为何合理 |
| --- | --- |
| 支付和取消都先读到状态1，支付先更新成2 | 取消仍要求旧状态1，更新0行并提示刷新，不能把已付款信息覆盖成未支付 |
| 支付已提交成2，取消随后读到状态2 | 取消从2变6并设模拟退款；支付与取消两个请求都可能成功，这是合法的先支付后取消 |
| 取消先把1改成6 | 支付 SQL 要求1，失败；已取消订单不会复活 |

因此准确目标是“每次迁移遵守合法旧状态、钱款状态一致”，不是“任何时序下只能一个 HTTP 请求成功”。H2 测试里固定双方都竞争旧状态1，才断言只有一方更新成功。

### 7. 重复支付的幂等边界

已经支付且仍有效的顺序重试会直接返回成功，不重复通知。如果两个支付请求同时先读到未支付，其中一个可能在条件更新时失败并要求刷新；这仍然保证不会支付两次，但不是保证所有并发重试都返回相同响应。

已取消/已退款订单不允许通过重复 payment 重新付款。支付 VO 仍保留原结构，但没有真实商户签名参数，也不调用真实扣款。

## 九、再来一单和催单

### 1. 再来一单不再照搬旧价格

旧做法从订单明细直接拷贝后批量插入购物车，容易保留旧价、生成重复 SKU，也缺少订单归属限制。

新顺序是：锁用户 → 确认订单属于自己 → 检查营业 → 读取原明细 → 校验全部商品/口味/数量并加载当前价 → 逐项 merge 到现有购物车。

原订单菜品6件，当前购物车已有相同口味1件，结果为7件，不清空原购物车。如果有一个商品下架或合并数量超限，整个事务回滚，不出现“前两道加上了、第三道失败”的半完成状态。

全量合法性检查先于合并；即便后面的合并才发现数量超限，外层事务也会撤销前面的合并。当前按旧订单内容重新验证，失效规格不会自动猜一种新口味替代。

### 2. 催单限制

`remind` 先检查订单归属，只允许状态2—4，并发送 type=2 通知。尚未付款、已完成、已取消订单不能催单。

为兼容原接口，它仍是 GET，但业务上有副作用，所以前端不能因为网络失败就自动重放。后端本轮没有增加催单频率限制或通知去重窗口。

### 3. 为什么通知放在事务提交之后

如果在支付事务提交前发送“新订单来了”，随后数据库事务失败，商家就收到了一个不存在的支付结果。

`notifyAfterCommit` 检查当前是否存在事务同步：有则注册 `afterCommit` 回调，提交后才发送；没有则直接发送，例如催单。type=1表示来单，type=2表示催单，保留原商家端消息结构。

这解决“先通知后回滚”的顺序问题，但**不等于可靠消息系统**：数据库提交之后进程退出、WebSocket断开仍可能导致通知丢失。没有新增消息表、重试队列或持久化 outbox，不能声称通知永不丢失。

## 十、管理端和定时任务受到什么影响

### 1. 管理端 Controller 没改，服务规则加强了

管理端仍通过原 `OrderService`。状态迁移现在统一由 `transition` 检查影响行数。

| 操作 | 允许的旧状态 | 目标状态/附加处理 |
| --- | --- | --- |
| 接单 confirm | 2待接单 | 3已接单 |
| 拒单 rejection | 2待接单 | 6已取消；已付则模拟退款，记录拒单原因与时间 |
| 商家取消 cancel | 非5/6的正常订单 | 6已取消；已付则模拟退款，记录取消原因与时间 |
| 派送 delivery | 3已接单 | 4派送中 |
| 完成 complete | 4派送中 | 5已完成，记录 deliveryTime |

原来接单等操作的普通更新可能将已取消记录改回进行中；现在旧状态不匹配就拒绝。管理端取消已完成订单也被禁止，不只是修前端按钮。

### 2. 查询逻辑变化

`pageQuery4User` 强制当前用户，增加 `pageNum>=1`、`1<=pageSize<=100`、非空状态范围1—6的校验。全部状态应不传 status，而不是向后端传0。

用户分页、商家条件搜索、详情通过 `view` 共用 VO 构建：包含订单明细列表，同时生成 `菜名*数量;` 的 orderDishes 展示串。原有统计仍按状态计数。

这是减少重复代码，不是新增高性能批量加载；当前每个订单仍需查询自己的明细，未解决列表的 N+1 查询问题。

### 3. 定时任务只改更新保护和启停，不重写调度规则

超时任务仍每分钟执行一次：找超过15分钟的待付款订单，再通过 `updateExpected(...,1)` 取消。若订单已经被支付改为2，旧任务更新不到，不会覆盖支付。

派送任务仍每天凌晨1点执行，并通过 `updateExpected(...,4)` 完成选中的派送中订单。

**注意代码与旧注释的差别：实际筛选依据仍是订单创建时间 `order_time < 当前时间减60分钟`，不是严格“前一天”，也不是按预计送达时间判断。** 本次未重新设计该业务规则；自动完成也没有像手动 complete 那样补写 deliveryTime。不要误以为整个定时配送逻辑已重构完善。

### 4. 新增调度开关

```java
@ConditionalOnProperty(
    name = "sky.order.scheduling-enabled",
    havingValue = "true",
    matchIfMissing = true
)
```

含义是：配置 true 或未配置时创建任务 Bean；false 时不创建，因此不会执行这两个定时任务。不是关闭整个 Spring 的所有定时任务。

之前自动联调启动参数使用 false，避免测试进程批量改变已有历史订单。即使任务关闭，支付接口自己的15分钟限制仍生效：订单可能暂时显示待付款，但已经不可支付。

## 十一、异常、日志与请求上下文

### 1. 这次真的遇到了表情存储错误

本地真实 MySQL 在订单备注含“🍜”时返回 `Incorrect string value`，错误码1366。前端可以正确处理 Unicode，并不代表当前数据库列/连接组合能够保存所有字符。

本轮默认不改表，因此没有静默改字符集或删掉用户表情，而是在全局异常处理器添加了有针对性的处理。

### 2. 数据库异常如何区分

新的 `databaseExceptionHandler(DataAccessException ex)` 沿异常 cause 链寻找 SQLException，同时满足错误码1366与消息包含 `Incorrect string value` 才识别为该字符问题。

| 情况 | HTTP/Result | 前端应怎么做 |
| --- | --- | --- |
| 已识别的不支持字符 | HTTP200，code0，明确文案 | 保留草稿，修改输入后再提交 |
| 其他 DataAccessException | HTTP500，通用提示 | 不假设操作必定没发生，先核对服务器状态 |
| 原有业务异常 BaseException | 保留原业务错误机制 | 展示相应业务提示 |

不能只判断1366：同一错误码也可能是其他非法字段值，所以还检查错误消息类型。响应不包含原始 SQL、数据库详细错误或用户原始输入。

### 3. 回滚是谁完成的

不是异常处理器执行 SQL 把数据“删回来”。顺序是：数据库出错 → 异常退出事务服务 → Spring回滚 → 异常到达ControllerAdvice → 转成前端能理解的响应。

真实联调已经验证失败订单没有生成，购物车原来1件仍保留；前端测试也验证草稿不清除、允许修改输入。这不表示所有没有事务的旧接口也自动具备相同的多步骤回滚保证。

异常处理器是全局的，不只影响用户订单。其他被 Spring 包装的数据库异常也会进入500分支，包括可能的唯一键冲突；并非保证所有管理端旧的细分数据库提示都原样保留。管理端全量异常回归未完成，见后面的边界说明。

### 4. 删除了哪些敏感日志

| 文件 | 不再输出的内容 |
| --- | --- |
| UserController | wx.login 的一次性 code |
| UserServiceImpl | 微信换取登录会话返回的完整 JSON |
| JwtTokenUserInterceptor | 用户完整 token |
| OssConfiguration | 包含访问密钥的 OSS 配置对象 |

修改日志只阻止这些位置今后继续输出，不能抹去已经存在的历史日志。此前出现过的凭证建议轮换；本次没有替你轮换密钥，也没有将密码或密钥写进本文。

本轮不是全系统日志脱敏审计。旧 Controller 仍有 DTO 日志，MyBatis debug 也可能记录参数。后续若用于真实用户环境，应另行检查个人信息日志、保留周期与访问权限，不能把上表理解成“全部日志都已脱敏”。

### 5. ThreadLocal 为什么要清理

`BaseContext` 通过线程局部变量存当前用户，方便深层 Service 获取身份。服务器线程会重复使用，不能把某次请求的数据永久留在线程上。

用户拦截器新增 `afterCompletion`，在请求完成后调用 `BaseContext.removeCurrentId()`。这是请求上下文生命周期清理，不是注销用户，也不会删除数据库用户或前端 token。

## 十四、当前边界和以后修改时的注意事项

以下是阅读代码后需要知道的边界，不是本文新增的修复，也不能当作已经验收通过。

1. **没有通用幂等键。** 用户锁保护同一批购物车消费；请求超时后客户端仍应先查订单，不能无脑重复提交。若两次请求之间又有人加了商品，那已经是新购物车内容，不能指望锁识别它是不是“同一次用户意图”。
2. **锁协议必须一致。** 新购物车/下单/地址写入口如果绕过 UserWriteLock，或直接从后台脚本写表，不自动受到完整业务保护。服务端仍可能发生锁等待和死锁错误，未实现自动重放写事务。
3. **商品和营业配置没有统一大锁。** 用户行锁不等于把商品表、营业开关和管理员改价全部冻结。本次按读取时的当前信息核价，没有实现商品库存预占、强一致停业切换等系统。
4. **完整表情存储尚未实现。** 已明确提示和验证回滚；若要支持，应另行检查库/表/列/连接字符集及迁移影响，不能只修改前端。
5. **共享服务和全局异常处理会影响管理端。** 已有2项管理端服务回归与真实WebSocket证据，未执行管理端浏览器全流程、所有唯一键/异常分支回归。
6. **真实双账号越权未完整联调。** 已在单元测试中构造他人记录并拒绝，没有把模拟用户ID测试冒充两个真实微信会话。
7. **定时任务未做长时间真实观察。** 联调时为保护历史数据关闭调度。SQL旧状态保护已测，不等于每分钟/凌晨任务都在运行环境实际执行过。
8. **通知不是持久化消息。** 无outbox、重试队列、催单限流，也未重做原WebSocket授权体系。
9. **测试不是全覆盖证明。** 23项通过、24接口成功，不等于所有状态组合、压力、数据库异常都验证完毕。
10. **生产安全是另一层工作。** 凭证轮换、全量日志脱敏、合法HTTPS域名、真实支付/退款、监控、备份与发布审核均不包含在这轮演示交付中。

保留这些边界是为了帮助你理解“这段代码已经保证什么、还没有保证什么”，而不是让绿色测试数掩盖实际限制。

## 十五、建议的代码阅读顺序与自测问题

### 1. 按一条真实请求读，不必一次读完29个文件

建议先看这条路径：

```text
用户 OrderController.submit
  → UserOrderService.submit
    → UserWriteLock.lock / UserMapper.lockById
    → AddressBookServiceImpl.getById
    → CartRules.hydrate
    → OrderMapper.insert / OrderDetailMapper.insertBatch
    → ShoppingCartMapper.deleteByUserId
```

第一遍只理解每一步“为了防什么”；第二遍再研究注解、BigDecimal、MyBatis占位符和事务传播。读完下单，再看 payment + payIfPending；随后看 cancel + updateExpected；最后读测试如何制造失败。

### 2. 六个问题检查自己是否真正理解

**问：前端按钮已经防重复点击了，为什么后端还要锁？**

答：按钮只约束这个界面；网络重试、另一个窗口、直接HTTP请求都能绕过。最终重复消费保护必须在服务端事务里完成。

**问：token没过期，能不能传别人的addressBookId下单？**

答：不能。有效token只说明身份，getById还要核对地址userId。

**问：给DTO加个@NotNull就能阻止改金额吗？**

答：不能。非空不等于价格可信。要从服务器商品数据重新算金额，并忽略客户端金额的权威性。

**问：为什么取消订单的SQL不只写where id=?？**

答：读取后到更新前可能已经付款/接单。额外旧状态条件用来防止迟到请求覆盖新状态。

**问：再来一单遇到一款下架，其他菜会不会已经加进去？**

答：先全量验证，再在一个事务里合并；任何失效或超量都会使整次操作失败并回滚，不部分加入。

**问：出现不支持的表情错误，为什么不直接删掉表情继续下单？**

答：静默改用户输入会掩盖数据问题，也可能改变备注含义。当前明确提示、保留输入和购物车，让用户决定；完整支持则另行做数据库迁移。

### 3. 最后用一句话总结

**此次后端修改把原来的“收到请求就按参数操作”，收紧为“先确认身份与权限，再按服务器数据核算，在事务和状态条件保护下写入，最后返回可核对的结果”。**

它提升了演示项目的正确性和可维护性，但保留了原有接口和框架；你以后改代码时，最应该保留的就是这些业务边界，而不只是文件名称或注解形式。
