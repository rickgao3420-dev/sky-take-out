# 根据类型查询分类 — 全流程数据分析报告

## 一、概览

"根据类型查询分类"接口用于按 `type`（1=菜品分类 / 2=套餐分类）筛选已启用的分类列表。该接口与分页查询不同——**不分页、只返回启用状态的记录**，主要用于前端下拉菜单和侧边栏导航。

> **核心特征**：SQL 中硬编码了 `WHERE status = 1`，**仅返回已启用的分类**。这就是为什么新创建的分类（默认 `status = 0`，禁用）虽然写入了数据库，却不会出现在前端页面上的**直接原因**。

| 层级 | 类/文件 | 核心方法/组件 |
|------|---------|-------------|
| 拦截器 | `JwtTokenAdminInterceptor` | `preHandle()` — JWT 校验 |
| Controller | `CategoryController` | `list()` — 接收请求，返回结果 |
| Service 接口 | `CategoryService` | `list()` 声明 |
| Service 实现 | `CategoryServiceImpl` | `list()` — 直接透传 |
| Mapper 接口 | `CategoryMapper` | `list()` 声明 |
| Mapper XML | `CategoryMapper.xml` | 动态 SQL（`<select id="list">`） |
| 消息转换 | `JacksonObjectMapper` | Java 对象 → JSON 序列化 |

## 二、请求入口 — 前端发起请求

### 2.1 HTTP 请求格式

```
GET /admin/category/list?type=1
Authorization: token <jwt_token>
```

| 参数 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `type` | Integer | 否 | 分类类型：`1`=菜品分类，`2`=套餐分类。**不传则查询所有类型的已启用分类** |
| Header `token` | String | 是 | JWT 令牌，由登录接口颁发 |

### 2.2 参数绑定机制

与分页查询不同的关键点：此处的 `type` 参数是一个**独立的 `Integer` 参数**，而非绑定到 DTO 对象。

```java
// Controller 方法签名
public Result<List<Category>> list(Integer type)
```

```
GET /admin/category/list?type=1
          ↓ Spring MVC 自动绑定（通过参数名匹配）
type = 1 (Integer)

GET /admin/category/list
          ↓ type 未传值
type = null (Integer)
```

> **原理**：Spring MVC 的 `RequestParamMethodArgumentResolver` 将 Query String 参数名与方法形参名一一匹配。参数类型为 `Integer`（包装类型），未传值时赋 `null` 而非基本类型的默认值 `0`，这是区分"不筛选"与"筛选 type=0"的关键设计。

## 三、拦截器层 — JWT 令牌校验

与员工分页查询共用同一拦截器链路，此处仅作简要回顾。

> **调用链路**：`DispatcherServlet.doDispatch()` → `JwtTokenAdminInterceptor.preHandle()` → 解析 token → 提取 `empId` → `BaseContext.setCurrentId(empId)` → 放行

**注意**：此接口为纯查询操作，并不消费 `BaseContext` 中的用户 ID。但 `preHandle()` 仍然会执行完整的 JWT 解析流程——任何未登录请求都在此处被拦截，Controller 方法不会执行。

## 四、Controller 层 — 接收请求与返回结果

**文件**：`CategoryController.java`

```java
@GetMapping("/list")
@ApiOperation("根据类型查询分类")
public Result<List<Category>> list(Integer type) {
    List<Category> list = categoryService.list(type);
    return Result.success(list);
}
```

### 4.1 方法签名对比

将此方法与分页查询的 Controller 方法对比：

| 维度 | 分页查询 `page()` | 列表查询 `list()` |
|------|------------------|-------------------|
| HTTP 方法 | `GET /admin/category/page` | `GET /admin/category/list` |
| 入参类型 | DTO 对象（`CategoryPageQueryDTO`） | 基本参数（`Integer type`） |
| 返回泛型 | `Result<PageResult>` | `Result<List<Category>>` |
| 分页 | ✅ PageHelper 分页 | ❌ 全量返回（仅受 `status=1` 限制） |

### 4.2 数据转换

```
Integer type (入参)
    ↓ 调用 Service
List<Category> (出参)
    ↓ 包装进 Result
Result<List<Category>> → Jackson 序列化 → JSON 响应
```

### 4.3 最终返回给前端的 JSON

{

> **关键特征**：响应体是一个**数组**（而非分页对象），前端拿到后直接渲染为下拉列表或侧边栏菜单，无需翻页。

## 五、Service 层 — 纯透传

**文件**：`CategoryServiceImpl.java`

```java
@Override
public List<Category> list(Integer type) {
    return categoryMapper.list(type);
}
```

### 5.1 极简设计的原因

此方法没有任何业务逻辑，直接调用 Mapper 并返回结果。原因如下：

1. **无需数据转换**：Mapper 返回的 `List<Category>` 即为前端所需的格式，不需要 DTO 转换
2. **无需分页**：分类数据量很小（通常不超过几十条），全量返回性能开销可忽略
3. **无需业务校验**：纯查询操作，不涉及数据完整性校验
4. **无需自动填充**：查询操作不修改数据库，`@AutoFill` 注解只用于 INSERT/UPDATE

### 5.2 与分页查询的 Service 层对比

```java
// 分页查询（pageQuery）—— 有业务逻辑
public PageResult pageQuery(CategoryPageQueryDTO dto) {
    PageHelper.startPage(dto.getPage(), dto.getPageSize());  // ① 启动分页
    Page<Category> page = categoryMapper.pageQuery(dto);     // ② 执行查询
    return new PageResult(page.getTotal(), page.getResult());// ③ 提取分页信息
}

// 列表查询（list）—— 纯透传
public List<Category> list(Integer type) {
    return categoryMapper.list(type);  // 一行搞定
}
```

## 六、Mapper 层 — SQL 执行

### 6.1 Mapper 接口

**文件**：`CategoryMapper.java`

```java
List<Category> list(Integer type);
```

> **设计注意**：返回类型是 `List<Category>` 而非 `Page<Category>`——这表明此方法不走 PageHelper 分页。无 `@AutoFill` 注解——这是只读查询，不触发自动填充。

### 6.2 动态 SQL

**文件**：`CategoryMapper.xml`

```xml
<select id="list" resultType="Category">
    select * from category
    where status = 1
    <if test="type != null">
        and type = #{type}
    </if>
    order by sort asc, create_time desc
</select>
```

### 6.3 `WHERE status = 1` — 最关键的硬编码过滤

这条 SQL 是整个问题的**核心机密**：

```sql
-- 当 type = 1 时：
SELECT * FROM category WHERE status = 1 AND type = 1 ORDER BY sort ASC, create_time DESC

-- 当 type 未传（null）时：
SELECT * FROM category WHERE status = 1 ORDER BY sort ASC, create_time DESC
```

> **结论**：该 SQL **无条件地只查询 `status = 1`（启用）的分类**。新创建的分类 `status = 0`（禁用）永远不会出现在查询结果中。这就是"数据库能写入但前端看不到"的根本原因。

### 6.4 `<if test="type != null">` — 可选条件过滤

```
当 type = 1 时:
  WHERE status = 1 AND type = 1 → 只返回启用的菜品分类

当 type = 2 时:
  WHERE status = 1 AND type = 2 → 只返回启用的套餐分类

当 type 未传（null）时:
  WHERE status = 1 → 返回所有启用的分类
```

> **原理**：MyBatis 的 `<if>` 标签在 OGNL 表达式中判断参数。`type != null` 意味着参数存在且不为 `null`。基本类型的包装类 `Integer` 允许 `null` 值，这是实现"可选参数"的关键。

### 6.5 `ORDER BY sort ASC, create_time DESC` — 排序规则

| 排序字段 | 方向 | 作用 |
|---------|------|------|
| `sort` | ASC（升序） | 按 sort 值从小到大排列，值越小越靠前 |
| `create_time` | DESC（降序） | 相同 sort 值时，后创建的分类排在前 |

> **业务含义**：管理员可以通过调整 `sort` 字段控制分类在前端的展示顺序（如"川菜"放在"粤菜"前面），同一 sort 值则按创建时间倒序。

### 6.6 结果映射原理

MyBatis 配置了 `map-underscore-to-camel-case: true`，自动将数据库字段映射到 Java 实体属性：

| 数据库字段 | Java 属性 | 类型 |
|-----------|----------|------|
| `id` | `id` | `Long` |
| `type` | `type` | `Integer` |
| `name` | `name` | `String` |
| `sort` | `sort` | `Integer` |
| `status` | `status` | `Integer` |
| `create_time` | `createTime` | `LocalDateTime` |
| `update_time` | `updateTime` | `LocalDateTime` |
| `create_user` | `createUser` | `Long` |
| `update_user` | `updateUser` | `Long` |

> **原理**：MyBatis 的 `ResultSetHandler` 对结果集中每一列名执行 `A_B` → `aB` 的驼峰转换，然后通过反射调用 `Category` 对象的对应 setter 方法（由 Lombok `@Data` 生成）。

## 七、序列化层 — 响应 JSON 的生成

**文件**：`JacksonObjectMapper.java` + `WebMvcConfiguration.java`

### 7.1 JSON 序列化过程

```
List<Category> (Java 对象)
    ↓ JacksonObjectMapper 序列化
[
    {"id": 1, "type": 1, "name": "川菜", ...},
    {"id": 3, "type": 1, "name": "粤菜", ...}
]
    ↓ MappingJackson2HttpMessageConverter
HTTP Response Body (Content-Type: application/json)
```

### 7.2 时间格式化

`Category` 实体的 `createTime` 和 `updateTime` 是 `LocalDateTime` 类型。`JacksonObjectMapper` 将其序列化为 `"yyyy-MM-dd HH:mm"` 格式：

```json
{
    "createTime": "2025-01-15 10:30",
    "updateTime": "2025-07-20 14:22"
}
```

> 如果不注册此自定义模块，Jackson 默认会将 `LocalDateTime` 序列化为 `[2025,1,15,10,30,0]` 数组格式。

## 九、关键设计要点总结

### 9.1 为什么新分类"写入了但看不到"

```
新增分类的完整链路:

① 前端提交 → POST /admin/category → save() 
② Java: category.setStatus(StatusConstant.DISABLE) → status = 0
③ SQL: INSERT INTO category (...) VALUES (..., 0, ...)
④ 数据库: 写入成功，status = 0

⑤ 前端刷新 → GET /admin/category/list → list()
⑥ SQL: SELECT * FROM category WHERE status = 1 → 过滤掉 status = 0 的记录
⑦ 前端: 列表为空（或旧数据），新的分类不显示
```

**解决路径**：调用 `POST /admin/category/status/1?id=<新分类ID>` 将分类状态改为 `1`（启用），之后 `list()` 接口就能返回了。

### 9.2 `list()` 与 `pageQuery()` 的设计差异

| 维度 | `list()` | `pageQuery()` |
|------|----------|---------------|
| 分页 | ❌ 不分页 | ✅ PageHelper 分页 |
| status 过滤 | ✅ `WHERE status = 1`（硬编码） | ❌ 不过滤（支持显示禁用项） |
| type 过滤 | ✅ 可选参数 | ✅ 可选参数 |
| name 搜索 | ❌ 不支持 | ✅ LIKE 模糊搜索 |
| 排序 | `sort ASC, create_time DESC` | `sort ASC, create_time DESC` |
| 返回类型 | `List<Category>` | `PageResult`（含 total + records） |
| 使用场景 | 下拉菜单、侧边栏 | 分类管理表格 |

> **设计意图**：
> - `list()` 面向**选择场景**（下拉框、导航栏），只应展示可用的分类，故硬编码 `status = 1`
> - `pageQuery()` 面向**管理场景**（管理后台表格），管理员需要看到包括禁用的所有分类，故不过滤 status

### 9.3 无分页设计的合理性

此接口不做分页，全量返回。原因：

1. **数据量极小**：一个餐饮系统的菜品/套餐分类总数通常不超过 50 条
2. **调用频率高**：每次打开新增菜品/套餐弹窗都需要调用，如果分页反而增加交互步骤
3. **前端需要全量**：下拉菜单需要所有可用分类，分页会让下拉菜单无法展示完整列表

### 9.4 `<if>` 动态 SQL 的可选参数模式

```xml
<if test="type != null">
    and type = #{type}
</if>
```

与 `${}` 字符串替换不同，`#{}` 使用 **PreparedStatement 预编译**，完全防止 SQL 注入。MyBatis 将 `#{type}` 替换为 `?`，由 JDBC 驱动安全传参。

### 9.5 layout 排序在前端的作用

```sql
ORDER BY sort ASC, create_time DESC
```

`sort` 字段是管理员手动设置的顺序值（如"川菜"=1，"粤菜"=2）。如果两个分类 sort 值相同，则按创建时间倒序（新的在前）。

当管理员在管理后台拖拽调整分类顺序时，实际修改的就是各分类的 `sort` 值。
