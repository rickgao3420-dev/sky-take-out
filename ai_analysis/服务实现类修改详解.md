# 后端服务实现类改动详解

整理日期：2026-10-14。

本文按 Git HEAD 与当前工作区差异，说明此次小程序配套重构涉及的服务实现类改动。范围包括 4 个已有实现类和 1 个新建的用户订单服务类；不把原来已经存在的登录、订单、地址、购物车功能说成本次新增。

## 总览：职责怎么变化

| 类 | 这次调整的重点 |
| --- | --- |
| `ShoppingCartServiceImpl` | 购物车写操作统一加用户锁和事务；SKU 精确匹配；服务器重建快照；数量合并与旧重复行归并 |
| `AddressBookServiceImpl` | 地址按当前用户过滤和校验归属；写操作加锁、事务；校验字段；默认地址切换串行化 |
| `OrderServiceImpl` | 收窄为共享/管理端订单查询与商家端操作；订单状态修改改用预期状态条件更新 |
| 新建 `UserOrderService` | 集中用户订单归属、下单、模拟支付、取消、再来一单、催单等用户端逻辑 |
| `UserServiceImpl` | 不再记录微信登录接口返回的完整响应，避免日志包含敏感凭证数据 |

这些类也都从字段注入改为构造器注入（Lombok `@RequiredArgsConstructor`）；这属于依赖声明方式整理，业务规则仍以各方法为主。

## 1. `ShoppingCartServiceImpl`：购物车写入规则变完整

### 旧实现

旧加购是：复制 DTO、从 `BaseContext` 取用户 ID、按 DTO 动态条件查询；查到一行就数量加一，没查到才查菜品/套餐并插入。旧减购也按 DTO 条件查询，再对第一条结果减一或删除。

这种写法短，但 SKU 是否匹配容易受 DTO 字段是否为 null 影响；命中旧行时不会刷新商品快照；旧重复行也不会一起归并；多个写请求没有共同的数据库排队点。

### 当前实现

- `addShoppingCart` 加 `@Transactional`，先调用 `UserWriteLock.lock()`，再检查营业状态。
- DTO 只提供商品选择信息；服务将 `userId` 设为登录用户，并通过 `CartRules.hydrate` 查当前菜品/套餐，验证上下架、规格和价格，填入最新名称、图片、价格。
- `merge` 以当前用户为查询范围，调用统一 `rules.same` 精确比较 SKU；同 SKU 累加数量，不同口味保留为不同项。
- 合并前后都检查数量范围；没有匹配项则插入；有匹配项则用 `updateSnapshot` 更新数量与商品快照。历史里存在多行完全相同 SKU 时，归并到一行并删除其余行。
- `subShoppingCart` 同样先锁用户，再验证请求的商品身份和口味，按完整 SKU 减一或删除。下架商品仍允许移除。
- `cleanShoppingCart` 改为事务内先锁用户，再按当前用户 ID 清空。
- `showShoppingCart` 仍是普通只读查询，不拿写锁。

用途：让加购、减购、清空和下单共用每用户的写入排队规则；把 SKU 与商品校验集中在 `CartRules`；下单时还会再次从商品表核价，购物车金额只作快照。

## 2. `AddressBookServiceImpl`：补上用户归属和写入校验

### 当前改动

- 依赖改为构造器注入，并注入 `UserWriteLock`。
- `list` 强制把 `userId` 设置为当前登录用户，避免调用方传入其他 userId 后越权查询。
- `getById` 不再只按 ID 返回数据；查不到或记录不属于当前用户时，抛出“地址不存在或无权访问”。因此更新、删除、默认地址操作可以复用同一归属检查。
- 新增地址时在事务中先锁用户，服务器覆盖 `userId`，校验字段，并强制新地址不是默认地址。
- 修改地址在事务中先锁用户、读取并确认旧记录归属，再校验输入；保留旧记录的性别字段，不把前端未传的值错误覆盖；`isDefault` 不允许通过普通编辑请求改变。
- 设默认地址在一个事务中先锁用户并检查地址归属，再将该用户所有地址改为非默认，最后把指定地址设为默认。
- 删除地址也在事务中先锁用户、确认归属再删除。
- 新增联系人、手机、地区、详细地址、标签等输入校验。

用途：把“当前用户可访问哪些地址”放到服务端强制执行；用事务加用户锁保护“先全部取消默认，再设一条默认”的多步操作，防止同一用户的并发地址写互相穿插。

## 3. `OrderServiceImpl`：从混合用户/商家逻辑收窄为共享与管理端服务

旧 `OrderServiceImpl` 同时承担用户下单、支付、支付成功回调、用户取消/再来一单/催单，以及商家管理端订单处理。当前工作区将用户端订单流程拆到了新建的 `UserOrderService`，因此该类显著变短、职责更集中。

当前保留的主要职责包括：

- 用户订单分页、订单详情等共用读取和 VO 构造；分页参数会检查合法范围。
- 管理端分页查询、订单统计。
- 商家接单、拒单、取消、配送、完成等状态流转。
- 通过 `required`、`cancelled`、`transition` 复用必要逻辑，减少每个操作重复写状态判断与更新代码。
- `transition` 调用 `orderMapper.updateExpected(update, expected)`，要求数据库里的当前状态仍等于预期旧状态，并检查影响行数。状态已变化时，不再无条件覆盖，而是提示刷新。

依赖也精简为订单和明细 mapper，改用构造器注入。商家端取消、拒单等需要一起修改订单字段的流程使用事务。

用途：把商家状态转换从“先查询判断、再无条件 update”调整为“SQL 最终再确认旧状态”，减少接单、取消、定时任务等并发覆盖。

## 4. 新建 `UserOrderService`：集中用户端订单业务

用户端订单逻辑从原 `OrderServiceImpl` 拆出来，新服务主要负责：

- `owned(id)`：读取订单并校验它属于当前登录用户；用户订单详情等先做此检查。
- `submit(dto)`：事务内先锁当前用户，检查营业状态和下单字段，确认地址归属，读取购物车；每行重新校验商品和规格、按服务器当前价格重算金额；然后插入订单、批量插入明细、清空购物车。任一步失败，事务可整体回滚。
- `payment(dto)`：按订单号和当前用户查单，检查支付方式、待付款状态、未支付状态和 15 分钟有效期；调用 `payIfPending`，由单条 SQL 再次核对订单归属、状态和期限。当前是模拟支付，不是真实扣款。
- `cancel(id)`：确认订单归属和状态，然后使用 `updateExpected` 条件更新，防止取消覆盖并发支付或其他状态流转。
- `repeat(id)`：锁用户，确认旧订单归属，按旧明细重建购物车商品；每行用当前商品数据重新校验和定价；全部验证通过后复用购物车 `merge`，追加到现有购物车，不清空原购物车。
- `remind(id)`：确认用户有权操作该订单后，发送催单通知。
- 订单状态变更通知通过事务提交后的回调触发，避免数据库回滚了但 WebSocket 通知已经发出。

用途：将用户身份、用户订单权限、下单核价和购物车消费等规则集中在用户订单边界，避免用户端和管理端共用一个大服务类时混淆职责。

## 5. `UserServiceImpl`：收敛敏感日志

微信登录时原来会把 `jscode2session` 接口响应 JSON 完整写入日志。该响应可能含有会话密钥等敏感内容。当前改为只记录“收到微信登录响应”的调试信息，不打印响应正文。

用途：保留排查登录流程的少量线索，同时避免把凭证内容写入普通应用日志。登录交换和 Redis 相关业务流程本身没有因此重做。

## 6. 这些实现类如何配合

```text
用户发起购物车写操作
  → ShoppingCartServiceImpl
  → UserWriteLock + CartRules
  → ShoppingCartMapper

用户提交订单
  → UserOrderService.submit
  → UserWriteLock + CartRules + AddressBookServiceImpl
  → OrderMapper / OrderDetailMapper / ShoppingCartMapper

商家推进订单状态
  → OrderServiceImpl
  → OrderMapper.updateExpected

用户支付模拟
  → UserOrderService.payment
  → OrderMapper.payIfPending
```

共同的设计方向是把规则放在合适层次：Service 负责业务权限和流程，支持类负责共享规则，Mapper SQL 负责最终的数据库条件。事务管理多步整体性；用户行锁协调同用户写操作；条件更新防止订单旧状态被覆盖；日志不输出敏感登录响应。

## 7. 总结

这次主要不是新增一堆业务功能，而是重新划分职责并补齐写入边界：购物车写操作有统一 SKU 校验和用户锁；地址服务强制用户归属并验证输入；用户订单流程从原混合订单服务拆分出来；订单状态流转改为条件更新；微信登录日志不再记录凭证响应。读代码时可以从 `ShoppingCartServiceImpl` 和 `UserOrderService` 看用户写链路，再看 `OrderServiceImpl` 的管理端状态转换。
