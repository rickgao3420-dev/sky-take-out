# 事务、用户行锁与条件更新详解

整理日期：2026-09-23。

适用项目：`sky-take-out` 后端。本篇结合当前下单、购物车和订单状态代码，解释“事务不等于防止所有并发”，以及事务、行锁、条件更新分别解决什么问题。

## 一句话先记住

- **事务**保证一组数据库写入要么整体提交，要么整体回滚。
- **行锁**让竞争同一把锁的事务按顺序执行，避免它们同时处理同一用户的购物车业务。
- **条件更新**把“检查旧状态”和“写入新状态”合并到一条 SQL 中，防止过期操作覆盖已经变化的订单。

它们关注的问题不同，通常需要配合使用。

## 1. 为什么有事务还会有并发问题

事务常见的性质可以用 ACID 概括。这里重点是原子性（Atomicity）：一个业务过程里的多项数据库更改作为一个整体提交；若过程中发生需要回滚的异常，这个事务已经做过的数据库更改会撤销。

本项目下单过程的业务组合大致是：

```text
读取并核验购物车
  → 计算金额、件数
  → 插入订单
  → 插入订单明细
  → 删除当前用户购物车
  → 提交事务
```

如果订单插入成功、明细插入时失败，事务可以回滚订单；如果删除购物车后又发生会触发回滚的异常，删除也会回滚。这样数据库不会只留下半张订单，也不会因为一次失败就永久丢掉购物车。

但事务本身不一定意味着“其他事务不能同时进来”。隔离级别和锁决定并发事务怎样观察彼此的数据；普通查询不自动替业务流程预留“这份购物车归我处理”的权利。比如两个下单请求 A、B 几乎同时开始：

```text
A：读取购物车 → 购物车有一份牛肉饭
B：读取购物车 → 也读到同一份牛肉饭
A：创建订单 A、订单明细 A、清空购物车 → 提交
B：创建订单 B、订单明细 B、清空购物车 → 提交
```

A、B 各自都可能完整提交，因此两个事务分别都满足“订单和明细一起成功”，但同一份购物车却被消费了两次。这不是事务原子性失效，而是事务之间缺少协调：**事务保证每一组写入内部完整，不自动决定多个请求谁先消费同一份业务数据。**

## 2. 行锁：同一个用户的写操作排队

### 什么是行锁

行锁是数据库对某一条记录加的锁。持有锁的事务提交或回滚之前，另一个要取得冲突锁的事务需要等待。

本项目通过用户表里当前用户那一行作为“排队点”：

```sql
SELECT id FROM user WHERE id = ? FOR UPDATE;
```

对应代码可看：

- [UserWriteLock.java](../sky-server/src/main/java/com/sky/service/support/UserWriteLock.java)
- [UserMapper.java](../sky-server/src/main/java/com/sky/mapper/UserMapper.java)
- [UserOrderService.java](../sky-server/src/main/java/com/sky/service/UserOrderService.java)

`UserWriteLock.lock()` 从登录上下文取用户 ID，再调用 `lockById`。下单、购物车增减/清空、再来一单，以及地址写入等相关写流程会在事务里先取得这把锁。锁住的虽然是 `user` 表中的一行，但它被当成该用户写操作的共同协调点：同一个用户的这些流程都争同一把锁。

### 下单的并发时间线

假设用户 U 同时点了两次下单：

```text
时间       请求 A                              请求 B
t1         开启事务，锁住 user(U)
t2         读取 U 的购物车
 t3                                             开启事务，尝试锁 user(U)，等待
 t4         建订单、建明细、删除 U 的购物车
 t5         提交；释放 user(U) 的锁
 t6                                             获得 user(U) 的锁
 t7                                             读取购物车，发现为空
 t8                                             返回“购物车为空”，不再生成第二单
```

关键不在于“锁住购物车查询结果”这句话，而在于：**所有可能改变或消费这份购物车的相关写事务，约定先锁同一个用户行，并且整个流程一直处于同一个数据库事务中。**因此读购物车、生成订单、清空购物车之间不会被同用户的另一个遵守协议的写请求插队。

### 用户行锁与购物车行锁的区别

这里选择锁用户行作为“每用户单一排队点”，不代表购物车的每条记录都被 `SELECT ... FOR UPDATE` 锁住。它有两个实际特点：

1. 同一用户的加购、下单等遵守此协议的写操作会互相排队，规则容易统一，即使购物车当前为空、没有可锁的购物车行，也仍然能取得用户行锁。
2. 这是较粗粒度的排队。同一用户改地址与改购物车也可能互相等待，即便两项数据本身无关；不同用户锁不同的用户行，通常可以并行处理。

行锁并不会自动拦住未使用同一协议的代码、手工 SQL 或其他系统写入购物车。并发保护成立的前提是所有相关写路径遵守一致的加锁顺序，并在持锁事务里完成相应业务。`FOR UPDATE` 也必须放在事务中使用，行锁通常持续到事务提交或回滚；如果在事务外执行，不能达到贯穿整个业务过程的排队效果。

## 3. 条件更新：不让旧决定覆盖新状态

行锁适合把一串相关写操作排队。订单状态则常常可以用另一种手段保护：**把预期旧状态写进 UPDATE 的 WHERE 条件**。

本项目的订单状态更新 SQL（见 [OrderMapper.xml](../sky-server/src/main/resources/mapper/OrderMapper.xml)）核心结构是：

```sql
UPDATE orders
SET status = :newStatus
WHERE id = :orderId
  AND status = :expectedStatus;
```

例如用户取消订单时，服务先读取订单状态，确认它当前为“待付款”或“待接单”，然后调用 `updateExpected`，把读取到的旧状态作为 `expectedStatus`。支付也使用 `payIfPending` 做类似的条件更新。服务会检查 SQL 影响行数是否为 1：

- `1` 行：执行更新时数据库里确实仍是预期状态，当前操作成功。
- `0` 行：订单已不存在或状态已经被其他请求改掉，当前操作不能按旧判断继续，服务提示状态已变化。

这是常说的“比较并交换”（compare-and-set）思路：只有当前值等于预期值，才把它换成新值。数据库对单条 UPDATE 原子执行条件判断与修改，避免“先读状态、稍后不加条件地覆盖”的时间窗口。

### 取消和支付争抢同一订单

订单当前是待付款。支付回调与取消请求接近同时到达：

```text
支付请求：尝试把 status=待付款 更新为 status=待接单
取消请求：尝试把 status=待付款 更新为 status=已取消
```

两条 SQL 都带 `WHERE id=? AND status=待付款`。其中一条先成功后，数据库中的 status 已改变；另一条再执行时不再匹配，影响 0 行。于是只会有一个基于“待付款”这一旧事实的操作获胜，另一个必须重新读取状态或向用户报告状态已变化。

如果写成无条件更新：

```sql
UPDATE orders SET status = :newStatus WHERE id = :orderId;
```

后一条到达的请求就可能把前一条已经完成的状态覆盖掉，例如把已取消订单覆盖成待接单。

### 条件更新不局限于状态

同一模式可以用于库存、余额、版本号、领取名额等：

```sql
UPDATE product
SET stock = stock - 1
WHERE id = :id AND stock >= 1;
```

检查影响行数，1 行代表成功扣减，0 行代表库存不足或记录不存在。这样比先读出库存、在应用中减一、再无条件写回更能抵御并发超卖。

## 4. 三种机制怎么搭配

| 机制 | 保护范围 | 典型目的 | 本项目示例 |
| --- | --- | --- | --- |
| 事务 | 一组数据库操作 | 一起提交或一起回滚 | 下单、插入明细、清空购物车 |
| 用户行锁 | 持锁事务之间的相关写流程 | 让同一用户的购物车相关操作依序处理 | 下单与加购争用 `user.id` 行锁 |
| 条件更新 | 一条更新语句所作用的记录 | 只允许从预期旧值变到新值 | 支付、取消订单时要求旧状态仍匹配 |

可以把三者想成：事务是“这张单上的几个数据库步骤不能拆开”；用户行锁是“同一用户的两个写任务先后排队”；条件更新是“最终落笔时再确认单据仍处于我预期的状态”。

事务与行锁在下单里一起使用：锁让同一用户的购物车写操作排队，事务让订单、明细、购物车消费共同提交。条件更新处理订单状态竞争：即使某请求先前读到合法状态，数据库写入时仍做最后一次状态校验。

## 5. 常见误解和边界

### “加了事务，肯定没有并发问题”

不对。事务原子性和并发互斥是不同保证。多个事务都可以各自完整地成功，但由于读取同一业务数据而导致重复处理。需要按场景采用锁、条件更新、唯一约束、幂等键或其他并发控制。

### “有了行锁，所有请求都被锁住了”

不对。行锁只影响争用同一行冲突锁的事务。不同用户的 user 行不同；普通读请求通常也不会因为另一个事务锁了该用户行就自动等待；没有遵守用户锁协议的写入也不会自动排队。

### “条件更新可以替代整个业务事务”

不对。条件更新特别适合保护单条记录上的状态转换，但无法单独保证多张表之间的多步一致性。下单仍需要事务把订单、明细和购物车变化组合起来。

### “影响行数为 0 一定是系统错误”

不一定。它常表示竞争中的另一个操作先改变了状态，或者请求已过期。应用需要区分并以合适方式提示，而不能仍把本次操作报告为成功。

### “行锁能保证点击两次只会创建一次订单”

本项目的用户锁能阻止两次请求同时消费同一份已有购物车：第二个请求获得锁后会重新看到购物车已空。它不是通用的请求幂等机制。对于支付渠道重试、外部回调、请求超时后重试等“同一命令重复送达”场景，通常还要设计业务幂等键、唯一索引或状态检查；锁的具体覆盖范围以实现代码为准。

## 6. 对照当前代码的阅读路线

1. 看 `UserOrderService.submit`：找到 `@Transactional`、`userWriteLock.lock()`、购物车读取、订单/明细写入和购物车删除的先后顺序。
2. 看 `UserWriteLock.lock` 与 `UserMapper.lockById`：确认登录用户 ID 如何进入 `SELECT ... FOR UPDATE`。
3. 看 `ShoppingCartServiceImpl`：确认加购、减购和清空也在事务中先拿同一用户锁，因而和下单共享排队点。
4. 看 `UserOrderService.cancel/payment` 与 `OrderMapper.xml`：确认旧状态如何放进更新条件，以及服务怎样利用影响行数判断竞争失败。

## 7. 总结

“事务不等于防止所有并发”说的是：事务能让一组变化保持整体性，但并不会自动替多个并发请求决定谁有权消费某份数据。当前实现为购物车和下单等同用户写流程提供共同的用户行锁，再用事务把每次下单涉及的多表修改绑定在一起；订单状态变化则用条件更新在数据库写入时验证旧状态。这样分别覆盖了**整体回滚、同用户写流程排队、状态转换不被陈旧请求覆盖**三个问题。
